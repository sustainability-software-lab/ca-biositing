## Rule
For any change to a SQLModel table or column:
1. Edit the model in `src/ca_biositing/datamodels/ca_biositing/datamodels/models/`. Add new models to `models/__init__.py`.
2. Run `pixi run migrate-autogenerate -m "<description>"` (or `pixi run alembic revision --autogenerate -m "..."`).
3. Review the new file in `alembic/versions/` before committing. Autogenerate misses column type changes and server defaults (`docs/pipeline/ALEMBIC_WORKFLOW.md`, step 3).
4. Apply with `pixi run migrate` and check with `pixi run -e py312 alembic check` (CI runs this).

## Why
- Alembic does not see views, and autogenerate can miss type and default changes.
- Nullability must match the model. `alembic/README` says `alembic check` fails with `modify_nullable` when a model’s Optional does not match a DB `NOT NULL`.

## Evidence in history
- Several table revisions are autogenerate output with the `# ### commands auto generated by Alembic - please adjust! ###` marker still present (for example `0013`, `0016`). Autogenerate is the normal path.
- `0007_adding_exper_tracking.py` is a no-op placeholder: autogenerate found nothing, so the revision was kept as `pass`.

## Exceptions
- Materialized views, data migrations, and downgrade logic are hand-written (see decisions/views-compiled-sql-snapshots).

## Verification
- CI: `.github/workflows/migrations.yml` runs `alembic upgrade head`, `alembic check`, and `alembic downgrade base`.
