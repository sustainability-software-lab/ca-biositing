## Purpose
Materialized views are not autogenerated, so this script compiles each SQLAlchemy expression with the PostgreSQL dialect and writes a complete migration file. The migration is the only thing that changes the live database.

## How it works
1. Import each view expression from `data_portal_views` and `views`.
2. Compile to SQL with the PostgreSQL dialect.
3. Write `alembic/versions/NNNN_<slug>.py` (or overwrite NNNN) with `DROP_INDEX_STATEMENTS`, `DROP_VIEW_STATEMENTS` (`... CASCADE`), one `*_SQL` string per view, `CREATE_INDEX_STATEMENTS`, and `GRANT` to `biocirv_readonly` (`upgrade`).
4. `downgrade()` only drops the same views and indexes. It does **not** recreate the previous definitions.

## Interfaces
- Input: `VIEWS` list plus current Python expressions.
- Output: one Alembic revision. Next steps printed by the script: `alembic downgrade -1` then `pixi run migrate` (for overwrites).
- Run from the repo root (paths are relative: `alembic/versions`).

## Gotchas
- Overwriting an already-applied revision with `--force` leaves the DB at the old definition. The script’s own message says to downgrade first. Downgrade drops the views, so run `refresh-views` or re-migrate afterwards.
- `downgrade -1` on a view migration leaves the database with no compiled views until the previous migration is re-applied (inferred from the template, which only drops).
- The `VIEWS` list omits `landiq_*`, `usda_survey_view`, `billion_ton_tileset_view`, `usda_resource_commodity_view`, `mv_biomass_county_production` and `mv_billion_ton_county_production`. Edits to those cannot be compiled with this script (inferred from the list; confirm before relying on it).
- Every compile regenerates all 13 views. Migration 0024 is several hundred lines of SQL, so apply time holds an exclusive lock on each view (inferred; confirm with a timing run).
- `-m` slugs are sanitized and can collide with an existing filename; check `alembic/versions/` before running.
