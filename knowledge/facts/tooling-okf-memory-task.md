## Purpose
Project memory for agents lives in the OKF (Open Knowledge Format) bundle at `knowledge/`. The `okf` CLI is not a Pixi dependency: the task fetches it into a cached temporary env.

## Key files
| Path | Role |
| --- | --- |
| pixi.toml:61 | `okf = { cmd = "pixi exec --spec \"okf-agent-memory>=0.5.0,<0.6\" -- okf" }` |
| knowledge/index.md | Bundle index; frontmatter `okf_version: "0.2"` |
| knowledge/log.md | Bundle write log |
| .agents/skills/okf-memory/ | Project skill that tells agents how to read and write the bundle |
| .pre-commit-config.yaml (prettier exclude) | Keeps prettier away from `knowledge/` |
| tests/agent_harness/test_okf.py | Checks the task command, the bundle init and the prettier carve-out |

## How it works
- `pixi run okf version` prints the CLI version; the spec is pinned to the 0.5.x series.
- `pixi exec` caches the environment outside `pixi.lock`, so no lock rewrite (consistent with the lock rule).

## Interfaces
- Inputs: `knowledge/` directory.
- Outputs: OKF concept files and regenerated `index.md`/`log.md` written by the CLI.
- Callers: agents via the `okf-memory` skill; developers via `pixi run okf`.

## Gotchas
- The bundle’s `index.md` and `log.md` are generated by the CLI; hand edits are overwritten on the next write.
- Wikilink and frontmatter clashes apply only if the bundle is rendered by mkdocs, which it is not (see `.agents/rules/mkdocs-okf-knowledge-bundle.md`).
- The CLI’s network fetch means the task needs network on first run.
